# ما الذي يديره الـ HR (لا شيء مكتوب في الكود)

| الإعداد | التحكم |
|---|---|
| مراحل الحضور | أي عدد من المراحل، لكل مرحلة: الاسم، اللون، الحد الزمني، نوعها (في الوقت/متأخر) |
| مرحلة الغياب | اسمها ولونها وخصمها (للغياب أو التأخر بعد آخر مرحلة) |
| بداية الدوام | وقت قابل للتعديل (وتُحسب منه دقائق التأخير) |
| الخصومات | لكل مرحلة: مبلغ ثابت / بالدقيقة / نسبة من الراتب اليومي / نسبة من الراتب |
| قواعد التعويض | أي مرحلة تُعوَّض بأي مرحلة وبكم نقطة (مثال: أحمر=1 أخضر، أسود=5 أخضر) |
| سياسة التعويض | أخضر بعد اليوم فقط أو أي أخضر، وترتيب المعالجة، وحد أقصى شهري، أو إيقافه |
| المكافأة | تفعيل، ثابتة أو نسبة، هل تُحتسب مع الأيام المعوَّضة، وعدد الأيام السيئة المسموح بها |
| الدوام | أيام العطلة الأسبوعية، ومقسوم الراتب اليومي (30 أو غيره) |
| العطل والإجازات | عطل رسمية، أنواع الإجازات (مدفوعة/غير مدفوعة)، الموافقات |
| العذر المقبول | الـ HR يعفي يوماً مع سبب (يُسجَّل في سجل التدقيق) |
| طرق التحقق لكل فرع | GPS / شبكة المكتب / بصمة، والنطاق والشبكات المسموحة |
| التطبيق | سياسة افتراضية للشركة، ثم لكل فرع، ثم لكل موظف (الأعلى أولوية) |

## ضمانات
- **تحقق قبل الحفظ:** `validatePolicy()` يرفض الأوقات غير المرتبة، والألوان الخاطئة، والتعويض بمرحلة غير موجودة.
- **نسخ مؤرخة:** أي تعديل ينشئ نسخة جديدة بتاريخ سريان؛ الأشهر السابقة لا تتغير، وكل ملخص شهري يحفظ السياسة التي حُسب بها.
- **معاينة قبل التطبيق (Simulate):** يجرّب الـ HR السياسة الجديدة على بيانات شهر سابق ويرى الفرق في الرواتب قبل اعتمادها.
- **سجل تدقيق:** من غيّر ماذا ومتى (قبل/بعد).

## واجهات الـ API المخطط لها
- `GET/POST /policies` · `PUT /policies/:id` (ينشئ نسخة) · `POST /policies/validate`
- `POST /policies/:id/simulate?year=&month=` (معاينة الفرق)
- `PUT /branches/:id/policy` · `PUT /users/:id/policy`
- `CRUD /holidays` · `/leave-types` · `POST /attendance/:id/excuse`
